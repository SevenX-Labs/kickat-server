KICKAT E-COMMERCE SERVER - CUSTOMER-SIDE RATE LIMITING ANALYSIS
================================================================================
Document Version : 1.0.0
Date Analyzed    : 2026-08-14
Target Server    : Kickat E-Commerce Backend (NestJS + Prisma + PostgreSQL)
Base URL Prefix  : /api/v1
Scope            : All Customer-Facing Endpoints & Infrastructure
================================================================================

--------------------------------------------------------------------------------
1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
Rate limiting on the customer-facing side is PARTIALLY IMPLEMENTED.

[YES] Application-Level Custom Rate Limiting:
      - Implemented specifically for OTP (One-Time Password) generation and
        verification across SMS and Email flows.
      - Backed by PostgreSQL (`otp_logs` table) to persist attempt counts across
        server restarts and distributed instances.

[NO]  Global / HTTP-Level Rate Limiting:
      - `@nestjs/throttler` (v6.5.0) is installed in `package.json`, but is NOT
        imported or registered in `AppModule` or `main.ts`.
      - There are NO global IP-based rate limiting guards or reverse-proxy rate
        limiters configured in the NestJS application layer.
      - Public browsing, product catalog, search queries, cart, checkout, and
        payment endpoints currently lack request throttling.

3. EXISTING RATE LIMITING IMPLEMENTATION DEEP DIVE
================================================================================

1. DATABASE SCHEMA:
   The database maintains a dedicated table `otp_logs` mapped to the Prisma
   `OtpLog` model:

   ```prisma
   model OtpLog {
     id         String   @id @default(uuid())
     identifier String   // E.g. Phone number (+91...) or Email address
     otpHash    String   // Bcrypt hash of 6-digit OTP
     type       OtpType  // SMS or EMAIL
     expiresAt  DateTime // 1 min (SMS) or 10 min (EMAIL)
     attempts   Int      @default(0)
     isUsed     Boolean  @default(false)
     createdAt  DateTime @default(now())

     @@index([identifier, createdAt])
     @@map("otp_logs")
   }
   ```

2. SEND OTP RATE LIMITING ALGORITHM:
   - Window: 1 Hour (Rolling 60 minutes)
   - Maximum Requests: 5 requests per identifier (phone / email)
   - Code Flow:
     ```typescript
     const oneHourAgo = new Date(Date.now() - 60 * 60 * 1000);
     const recentOtpCount = await this.prisma.otpLog.count({
       where: {
         identifier: phoneOrEmail,
         createdAt: { gte: oneHourAgo },
       },
     });

     if (recentOtpCount >= 5) {
       throw new HttpException(
         'Rate limit exceeded — max 5 per hour per identifier',
         HttpStatus.TOO_MANY_REQUESTS // 429
       );
     }
     ```

3. VERIFY OTP ATTEMPTS RATE LIMITING ALGORITHM:
   - Window: 1 Hour (Rolling 60 minutes)
   - Maximum Failed/Total Attempts: 5 attempts per identifier
   - Code Flow:
     ```typescript
     const attemptsCount = await this.prisma.otpLog.aggregate({
       where: {
         identifier: targetIdentifier,
         createdAt: { gte: oneHourAgo },
       },
       _sum: { attempts: true },
     });

     const totalAttempts = attemptsCount._sum.attempts || 0;
     if (totalAttempts >= 5) {
       throw new HttpException(
         'Too many attempts — max 5 per hour',
         HttpStatus.TOO_MANY_REQUESTS // 429
       );
     }
     ```
   - On failed comparison (`bcrypt.compare` mismatch), `attempts` is incremented:
     ```typescript
     await this.prisma.otpLog.update({
       where: { id: latestOtp.id },
       data: { attempts: { increment: 1 } },
     });
     ```

4. IDENTIFIED SECURITY & PERFORMANCE GAPS
================================================================================

1. Missing Global IP Throttling:
   - `@nestjs/throttler` is present in `package.json` dependencies but is unused.
   - An attacker can flood any public GET/POST endpoint from a single IP without
     triggering HTTP 429.

2. Unthrottled Search & Catalog Scraping:
   - `/api/v1/search`, `/api/v1/search/suggestions`, and `/api/v1/products` run
     intensive database queries (ILIKE text matching, joins, relations).
   - Without rate limits, bots can cause high CPU / database connection spikes.

3. Unthrottled Token Refresh & Auth Endpoints:
   - `POST /api/v1/auth/refresh` has no throttling, allowing high-frequency token
     rotation abuse.
   - `POST /api/v1/auth/google` is not rate-limited.

4. Guest Cart Flooding:
   - `POST /api/v1/cart/guest` accepts arbitrary guest cart items without user
     authentication or rate limit, which could be used to bloat the database.

5. Review Voting Manipulation:
   - `PATCH /api/v1/reviews/:id/helpful` has no rate limiter, allowing rapid
     repeated calls by an authenticated user.

5. RECOMMENDED NEXT STEPS TO ENABLE FULL RATE LIMITING
================================================================================

Step 1: Activate `@nestjs/throttler` globally in `AppModule`:
   ```typescript
   import { ThrottlerModule, ThrottlerGuard } from '@nestjs/throttler';
   import { APP_GUARD } from '@nestjs/core';

   @Module({
     imports: [
       ThrottlerModule.forRoot([{
         ttl: 60000, // 60 seconds
         limit: 100, // 100 requests per minute per IP
       }]),
       // other modules...
     ],
     providers: [
       {
         provide: APP_GUARD,
         useClass: ThrottlerGuard,
       },
     ],
   })
   export class AppModule {}
   ```

Step 2: Add stricter route-level `@Throttle()` decorators on sensitive endpoints:
   - Search: `@Throttle({ default: { limit: 30, ttl: 60000 } })` (30 req/min)
   - Auth Refresh: `@Throttle({ default: { limit: 10, ttl: 60000 } })` (10 req/min)
   - Guest Cart: `@Throttle({ default: { limit: 20, ttl: 60000 } })` (20 req/min)
   - Checkout / Payment: `@Throttle({ default: { limit: 10, ttl: 60000 } })` (10 req/min)

Step 3: Keep existing DB-backed OTP rate limiter for multi-device SMS/Email
        quotas, combining it with the IP-level ThrottlerGuard for defense-in-depth.
