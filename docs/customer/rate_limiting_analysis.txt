--------------------------------------------------------------------------------
1. EXECUTIVE SUMMARY
--------------------------------------------------------------------------------
Rate limiting and abuse protection on the customer-facing side has been significantly
strengthened with a multi-layered defense-in-depth architecture.

[YES] Application-Level DB Quotas (PostgreSQL `otp_logs` table):
      - Preserves persistent hourly quotas across server restarts and crashes.
      - SMS OTP: 5 requests / hour / phone on send, 5 attempts / hour / phone on verify.
      - Email OTP: 5 requests / hour / email on send, 5 attempts / hour / email on verify.

[YES] In-Memory / LRU Cache Layer (`OtpCacheService`):
      - Fast, synchronous, zero-delay in-memory state tracking via `lru-cache`.
      - 60-Second Cooldown on OTP Send: Enforces 1 send per 60 seconds per phone/email.
        Prevents rapid spamming before DB query execution.
      - Isolated Key Namespaces:
        * Auth SMS:   `otp:cooldown:phone:{phone}`
        * Auth Email: `otp:cooldown:email:{email}`
        * User Mobile Verification: `otp:cooldown:user-phone:{phone}`
        * User Email Verification:  `otp:cooldown:user-email:{email}`
      - Per-OTP Attempt Limit: Enforces a maximum of 5 failed attempts per individual
        generated OTP (`otp:attempts:{otpId}`). Upon the 5th failed attempt, the OTP is
        immediately marked `isUsed = true` and further attempts are rejected with HTTP 429.
      - Single-Use Enforcement: Validated OTPs are immediately invalidated.
      - Standardized 5-Minute Expiry across all SMS and Email flows.
      - Clean `IOtpCacheService` abstraction ready for seamless future Redis migration.

[YES] IP-Level Protection via `@nestjs/throttler` (v6.5.0):
      - Configured with named throttlers in `AppModule`:
        * `otp-send-short`: 3 requests / 10 minutes / IP
        * `otp-send-long`: 20 requests / hour / IP
        * `otp-verify`: 20 attempts / hour / IP
      - Enforced via `@UseGuards(ThrottlerGuard)` and route-level `@Throttle` in
        `AuthController` and `UsersController`.
      - `@SkipThrottle()` applied to non-OTP routes (e.g. `/users/me`, Google OAuth).
      - Google OAuth Rate Limit: Custom IP-based rate limiting (10 requests / hour / IP).

[PARTIAL] General Public Endpoints (Search, Catalog, Guest Cart):
      - Sensitive authentication and verification flows are fully protected.
      - General catalog browsing and guest cart endpoints remain unthrottled at the
        application layer (can be protected with reverse proxy / Cloudflare WAF).

3. MULTI-LAYER RATE LIMITING & SECURITY ARCHITECTURE
================================================================================

1. DEFENSE-IN-DEPTH OTP PIPELINE:

   Incoming Request (Send OTP)
        │
        ▼
   [Layer 1: IP ThrottlerGuard] ───> Exceeds 3 req / 10m OR 20 req / hr ──> HTTP 429
        │ (Passed)
        ▼
   [Layer 2: LRU Cooldown Check] ──> Cooldown active (< 60s since last) ─> HTTP 429
        │ (Passed)
        ▼
   [Layer 3: DB Hourly Quota] ─────> Count >= 5 requests in last 1 hour ─> HTTP 429
        │ (Passed)
        ▼
   [Layer 4: Generate & Dispatch OTP]
        │
        ├─ Standardize 5-minute expiry (`Date.now() + 5 * 60 * 1000`)
        ├─ Set 60s cooldown in LRU cache (`otpCacheService.setCooldown`)
        ├─ Persist OTP record in PostgreSQL (`otp_logs`)
        └─ Mask logs (no raw OTPs, masked email/phone)

   Incoming Request (Verify OTP)
        │
        ▼
   [Layer 1: IP ThrottlerGuard] ───> Exceeds 20 attempts / hr / IP ───────> HTTP 429
        │ (Passed)
        ▼
   [Layer 2: DB Hourly Quota] ─────> Total attempts >= 5 in last 1 hour ──> HTTP 429
        │ (Passed)
        ▼
   [Layer 3: Per-OTP Attempt Limit] > Failed attempts >= 5 ───────────────> Invalidate OTP & HTTP 429
        │ (Passed)
        ▼
   [Layer 4: Verify Bcrypt Hash] ───> Mismatch ────────────────────────────> Increment LRU + DB
        │                                                                     (if 5th failure -> HTTP 429,
        │                                                                      else HTTP 401)
        ▼ (Match)
   [Layer 5: Invalidate & Mark Used]
        ├─ `isUsed = true` (Single-Use OTP enforcement)
        ├─ Clear attempt counter in LRU cache
        └─ Update user verification flag (`isEmailVerified` / `isPhoneVerified`)

2. DATABASE SCHEMA (`prisma/schema.prisma`):
   ```prisma
   model OtpLog {
     id         String   @id @default(uuid())
     identifier String   // E.g. Phone (+91...) or Email
     otpHash    String   // Bcrypt hash of 6-digit OTP
     type       OtpType  // SMS or EMAIL
     expiresAt  DateTime // 5 minutes across all channels
     attempts   Int      @default(0)
     isUsed     Boolean  @default(false)
     createdAt  DateTime @default(now())

     @@index([identifier, createdAt])
     @@map("otp_logs")
   }
   ```

3. IN-MEMORY LRU CACHE (`src/common/services/otp-cache.service.ts`):
   - Fast, zero-overhead atomic state tracking without external service dependencies.
   - Clean interface `IOtpCacheService` enables future drop-in replacement with Redis.
   - Keys & TTLs:
     * `otp:cooldown:phone:{phone}` (TTL 60s)
     * `otp:cooldown:email:{email}` (TTL 60s)
     * `otp:cooldown:user-phone:{phone}` (TTL 60s)
     * `otp:cooldown:user-email:{email}` (TTL 60s)
     * `otp:attempts:{otpId}` (TTL 5m)

4. THROTTLER CONFIGURATION (`src/app.module.ts`):
   ```typescript

     {
   ```

================================================================================
4. REMAINING IDENTIFIED SECURITY & PERFORMANCE GAPS
================================================================================

1. Unthrottled Search & Catalog Scraping:
   - `/api/v1/search`, `/api/v1/search/suggestions`, and `/api/v1/products` run
     intensive database queries (ILIKE text matching, joins, relations).
   - Without application or reverse-proxy limits, bots can cause elevated database load.

2. Guest Cart Operations:
   - `POST /api/v1/cart/guest` creates cart items for unauthenticated users without
     IP rate limiting.

3. Review Voting:
   - `PATCH /api/v1/reviews/:id/helpful` has no rate limiter, allowing rapid
     repeated calls by an authenticated user.

================================================================================
5. RECOMMENDED NEXT STEPS FOR GENERAL APPLICATION PROTECTION
================================================================================

Step 1: Configure global fallback or route-specific `@Throttle` decorators for
        non-auth public endpoints:
        - Search: `@Throttle({ default: { limit: 30, ttl: 60000 } })` (30 req/min/IP)
        - Guest Cart: `@Throttle({ default: { limit: 20, ttl: 60000 } })` (20 req/min/IP)

Step 2: When migrating to a multi-instance / distributed cluster in the future:
        - Replace `OtpCacheService` internals with Redis (or Redis cluster / Upstash).
        - Replace `@nestjs/throttler` in-memory storage with `ThrottlerStorageRedisService`.
        - The `IOtpCacheService` interface guarantees zero changes needed in controller
          or service business logic.
